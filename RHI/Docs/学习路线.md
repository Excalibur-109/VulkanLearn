# RHI 学习路线

本项目的目标是让同一段渲染前端代码能够在 D3D11、D3D12 与 Vulkan 上运行。阅读时不必同时理解三个原生 API；先掌握 RHI 的调用顺序，再选择一个后端追踪即可。

## 推荐顺序

1. `Include/RHI/RHICommon.hpp` 和 `Include/RHI/RHIHandles.hpp`：先认识结果码、格式、资源状态与强类型句柄。
2. `Include/RHI/RHIResources.hpp`、`Include/RHI/RHIPipeline.hpp` 和 `Include/RHI/RHICommands.hpp`：了解“创建什么资源”和“录制什么命令”。
3. `Include/RHI/RHIDevice.hpp`：这是前端唯一需要依赖的设备接口。
4. `Source/RHIContext.cpp` 与 `Source/RHIBackendRegistry.cpp`：理解后端注册和运行时切换如何保证旧设备仍可用。
5. `Include/RHI/PBR/RHIPBRRenderer.hpp` 与 `Source/RHIPBRRenderer.cpp`：这是最小完整绘制路径，适合第一次逐行阅读。
6. `Examples/PBROffscreenCheck.cpp`：观察应用层如何准备纹理、着色器、常量并发起绘制。
7. 后端实现：按 `D3D11 -> D3D12 -> Vulkan` 的顺序。D3D11 状态机最直观；D3D12 引入命令分配器和围栏；Vulkan 最接近显式资源与同步模型。

## 一次 PBR 绘制的调用链

```text
PBROffscreenCheck
  -> 后端工厂创建 IRHIDevice
  -> RHIPBRRenderer::Create
       -> 创建并上传 UV 球顶点/索引缓冲区
       -> 创建着色器模块与图形管线
  -> RHIPBRRenderer::Render
       -> 创建命令列表并开始录制
       -> 开始渲染区域，清除颜色附件
       -> 绑定管线、视口、常量和网格
       -> DrawIndexed
       -> 结束命令列表并提交到图形队列
  -> WaitIdle，销毁前端资源
```

每一层只负责自己的事情：示例负责组装输入，PBR 渲染器负责通用绘制顺序，RHI 接口描述意图，后端把意图翻译为原生 API 调用。

## RHI 与后端概念对应

| RHI 概念 | D3D11 | D3D12 | Vulkan |
| --- | --- | --- | --- |
| `IRHIDevice` | `ID3D11Device` + immediate context | `ID3D12Device` + command queue | `VkDevice` + `VkQueue` |
| `IRHICommandList` | 前端状态记录，调用时写入 immediate context | `ID3D12GraphicsCommandList` | `VkCommandBuffer` |
| `RHIGraphicsPipelineHandle` | 输入布局、着色器与状态对象的组合 | root signature + PSO | `VkPipelineLayout` + `VkPipeline` |
| `RHITextureViewHandle` | `ID3D11RenderTargetView` | RTV descriptor heap 中的描述符 | `VkImageView` |
| `RHIFenceHandle` | 事件查询/上下文同步的简化映射 | `ID3D12Fence` | `VkFence` |

表格用于理解，不代表三种 API 具有完全相同的能力或生命周期。RHI 只抽象调用方真正需要的公共语义；原生后端仍必须处理各自的限制。

## 最小 PBR 路径的边界

目前验证的路径包含：离屏颜色纹理、动态渲染区域、一个顶点缓冲区、一个索引缓冲区、128 字节推送常量、一个图形管线和一次索引绘制。`RHIPBRRenderer` 生成 UV 球，并使用 Cook-Torrance 金属度-粗糙度 BRDF 计算直接光照。

接口中仍有计算、光线追踪、描述符绑定集、复制、查询和交换链等能力定义。三个教学后端对尚未实现的能力会返回 `Unsupported`，这是有意保留的边界：它让接口可演进，同时避免示例把未实现功能伪装成可用功能。

## 阅读后端时的固定问题

对任何一个资源创建函数，依次回答四个问题：原生对象是什么？它的内存或描述符在哪里？RHI 句柄如何注册？失败时如何回收？

对任何一个命令列表函数，依次回答四个问题：允许在哪个命令列表状态调用？它改变了什么 GPU 状态？依赖哪些先前绑定？何时能提交？使用这套问题阅读三个后端，可以看见它们表面不同、语义相同的部分。
